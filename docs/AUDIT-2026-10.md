# EOB Reader audit, 8 October 2026

Live site: https://eob-reader.vercel.app. Repo default branch: `main` (last commit before this work: `f54f238`, 13 September 2026, keep-alive only).

Checked against the code in this repo, a logged-out local run of the landing page, and the 8 October logged-out browser notes. The 28 September repo notes were re-checked. The product claims below were still in the code. Signed-in screens were reviewed in source. This environment has no Supabase project, so upload, review, export, and billing were not clicked through while signed in.

What it is: a learning project for US dental offices. It reads the text layer of an EOB PDF, asks a model to draft line items, keeps a human review step, and exports an X12 835 file or a PMS CSV (Dentrix, Eaglesoft, Open Dental). It is not a HIPAA product.

Hours below are rough, focused work for someone who already knows the repo. The day total assumes 3 to 4 of those hours in a day.

## (a) Must-fix honesty and safety

About **13 hours**. The copy, public policy pages, portfolio notice, and README are in this pull request. Two safety holes are listed here and left alone because fixing them changes billing enforcement or the auth redirect.

1. **HIPAA, BAA, 90-day deletion, audit log, AES/TLS version, hashed passwords, Groq, and “guaranteed” were false.** Landing said “Designed for HIPAA Compliance” and “encrypted at rest, auto-deleted after 90 days, and never used to train third-party AI models. Ultimate privacy, guaranteed.” `/hipaa` said EOB Reader is a business associate, that a BAA is given to every customer during onboarding, that the workforce is trained, that risk assessments exist, AES-256, TLS 1.3, hashed passwords, “AI Providers (e.g., Groq)”, original images sent to the model, a 6-year audit log, and 72-hour breach notice. Privacy and terms repeated that. Settings showed green checks for 90-day deletion and “never used to train AI models.” Billing said “HIPAA-Compliant Billing.” **What the code does:** email OTP plus Google (no passwords), text sent to OpenRouter `openai/gpt-4o-mini` (optional local Ollama), no retention or no-training flag on that request, no BAA file, no deletion job (the only cron-style route is `/api/keep-alive`), `audit_log` is never written. **2 hours** to strip the claims. Done in this PR: `/hipaa` is now a short data note, and the footer link says “Data handling.”

2. **`/privacy`, `/terms`, `/hipaa`, and any unknown path sent logged-out visitors to `/login`.** `src/lib/supabase/middleware.ts` only treated `/`, `/login`, `/signup`, `/auth/callback`, and `/api/keep-alive` as public. There is no `/demo` or `/pricing` page, so those URLs also landed on login. **1 hour.** Privacy, terms, and the data note are public in this PR. Unknown URLs still redirect to login. That leftover is in (b).

3. **Overclaims.** “Hundreds of pages in under a minute.” “Parses line items instantly.” “Perfectly balanced CSVs.” “No manual data entry required.” “Approve extraction perfectly aligned beside the PDF” (the PDF opens in a dialog, not beside the draft). Billing: “extract them simultaneously in seconds,” “CSV/Excel,” “Priority Support” from engineers. The guide said export eliminates manual data entry, and the FAQ said a CSV cannot be imported even though CSV export exists. Extraction is a text-model draft. Review is required. The 835 builder can invent CO-45 or OA-23 lines so the file balances, which is not the same as a perfectly read EOB. **2 hours.** Softened in this PR. The review step is described as the point of the product.

4. **`hipaa@eobreader.com`, `privacy@eobreader.com`, and `support@eobreader.com` cannot receive mail.** eobreader.com is a parked domain. **0.5 hour.** Replaced with shanifadhil33@gmail.com.

5. **No warning that this is a portfolio project before someone uploads a real EOB.** **2 hours.** A notice is on the landing page, login, signup, and the signed-in shell: “Portfolio project. Use fictional data only. Not for real patient information.”

6. **README was the unmodified create-next-app text.** **1 hour.** Replaced with a short description of what the app does and what it does not do.

7. **A signed-in user can grant themselves Pro and reset the daily upload cap.** `practices` RLS is `FOR ALL` where `auth_id = auth.uid()`, including after migration 003’s `WITH CHECK`. The browser client updates `name` and `default_pms` from Settings, and the upload route updates `daily_upload_count` with that same user client. Nothing stops `subscription_status: "pro"` or `daily_upload_count: 0` from the browser. The Polar webhook uses the service role, so a column lock has to keep those server writes working. **3 hours.** Not changed in this PR. See Decisions.

8. **Auth callback open redirect.** `/auth/callback` reads `next` and redirects to `origin + next` after a valid code exchange. `next=@evil.com` becomes a URL whose host is `evil.com` (`https://<app-host>@evil.com`). The happy path does not pass `next`. **1 hour.** Not changed in this PR. See Decisions.

## (b) UI and behavior

About **49 hours**. Includes the public demo, which is scoped here and not built. Mobile rules and “nothing dead” apply on every screen. The checklist was used as a pick-list: this is a portfolio demo plus a small signed-in tool, so demo entry, review, export, settings, and phone layout matter. Team roles, a notification center, and a command palette do not.

9. **No public demo.** A stranger must create an account to see a batch, a review, or an export. The portfolio thumbnail is the login screen. There is no “use a sample file” action. **Scope, about 12 hours, not in this PR:** a read-only `/demo` that is public in the proxy, with obviously fictional patients (not realistic-looking names and dollar amounts presented as live data), a sample text-based PDF, one batch in mixed statuses (pending, flagged, approved), search and sort that actually change order, and the export download built from that seed. No signup wall. A “Reset demo” control. Demo data must not appear inside a real signed-in account. Empty state for a real account stays “upload your first PDF.” Label it as a demo. Phone layout of that screen is part of the same work.

10. **Phone layout is a shrunk desktop layout.** Checked in code, and the logged-out landing was screenshotted at 390px. Landing itself did not scroll sideways. Signed-in problems: the dashboard file-remove control is `opacity-0` until hover, so it is missing on a thumb; batch rows put a badge, delete, and arrow in one non-wrapping row; the review line-item table is `whitespace-nowrap` inside a horizontal scroller (acceptable only if the page itself does not scroll sideways); primary destinations sit in a hamburger, not a reachable bar; hover lift (`hover:-translate-y-2` on landing cards, `hover:-translate-y-1` on the hero button) is not gated on `@media (hover: hover)`; several icon buttons are under 44px. **8 hours** for a phone pass: cards instead of the wide table, visible remove, no press-scale on scrolling cards, 44px targets, no sideways page scroll at 320–430px.

11. **Sign out is one tap, in the sidebar, the mobile menu, and Settings.** No confirm, no “Signing out…” state, and it uses `router.push("/login")` rather than a hard navigation to the landing page. The checklist’s rule is a small confirm, then a busy button until the next screen paints, and an error only on a real failure. **3 hours.**

12. **Settings, billing, guide, and history are dead ends on a phone.** No in-app Back. The logo goes to the dashboard, which is good, but the other screens depend on the browser back button or the hamburger. Batch and export do have a back control. **3 hours.**

13. **Onboarding is white text on a white page.** `globals.css` sets `--background` to white. Onboarding uses `text-white`, `bg-white/5`, and `placeholder:text-white/25`. A new Google user is sent there for about two minutes after signup (`auth/callback`). The email OTP path almost never sends them, because `handle_new_user` always writes a name, and login only redirects when `practice.name` is empty. The onboarding page’s own “existing user” check uses five minutes, not two. **2 hours.**

14. **Unknown URLs redirect to `/login` instead of a 404 with a way home.** **2 hours.**

15. **Toasts never render.** `toast()` is used on login, signup, upload, settings, and history. `src/components/ui/sonner.tsx` exists and is never mounted. **1 hour.**

16. **Dashboard “Total Exported” is always 0.** The loader never sets `totalExported`. “Pending Review” is `total_eobs - approved_eobs`, so rejected rows count as pending. The upload success toast says every file started processing and ignores `errors` in the response, including skipped scans. **3 hours.**

17. **Deletes use `window.confirm`.** Focus rings are the browser default (`outline-ring/50` on every element), so a tap can leave a ring. There is no `loading.tsx`, so route changes can flash. Short lists such as PMS choice are buttons, which is fine. The history filter is also buttons. **4 hours.**

18. **The landing header says “Log in” and “Sign in with Google.”** The Google button goes to `/signup`. It does not start Google. Signup and login are the same email-code-plus-Google flow, with two pages. The checklist would show one Sign in when both doors are the same. **1 hour** of UI, and it is a decision because this PR does not change signup or auth. See Decisions.

19. **The hero preview uses “John Smith” and real-looking CDT dollars.** Fine as a sketch. On a demo it should be obviously fictional. **1 hour**, easiest inside the demo work. Counted on its own so it is not forgotten if the demo slips.

20. **Side-by-side review is not built.** “View PDF” opens a dialog. A real beside-the-PDF review, which the old headline promised, is **6 hours** if Adhil wants that layout. The headline no longer promises it.

21. **The PMS guide’s click-paths are unverified** against current Dentrix, Eaglesoft, and Open Dental menus. The FAQ contradiction (CSV vs 835) is corrected in this PR. Checking or labeling the steps as unverified is **3 hours**.

Logged-out landing at 390px: no sideways scroll, the menu button works in code, and the hero stacks. That is not a pass of the signed-in app.

## (c) Backend

About **47 hours**.

22. **Scanned PDFs are skipped.** Upload reads `getTextContent()` in the browser. Empty text becomes `"no text could be extracted (scanned PDF?)"` and no extraction row is stored. There is no OCR or vision path. The Ollama branch comment mentions a vision model and still sends text. **10 hours** for a real scan path, or a clear in-product error if scans stay out of scope. The skip should stay visible either way.

23. **Multi-patient EOBs keep one patient.** The prompt says to return an array. `response_format: { type: "json_object" }` will not return a top-level array. If an array does come back, the code returns `parsed[0]`. A wrapper such as `{ extractions: [...] }` is stored as one object and the fields come out empty. **5 hours.**

24. **`subscriber_name` is extracted and then dropped.** The column exists. The upload insert does not write it. The 835 export reads `subscriber_name` from the row, so it is always empty. **1 hour.**

25. **The server trusts the browser’s text.** `texts` in the form is whatever the client sends. It is not checked against the PDF. A client can store one PDF and send different text to the model. **3 hours** to extract text on the server from the stored file.

26. **Skipped files are orphaned, and nothing expires.** The PDF is uploaded to `eob-pdfs` before the text check. Batch delete only removes paths that have an `eob_extractions` row. There is no 90-day job. The daily counter increments by `files.length` even when some files fail, and two overlapping uploads can both read the old count. **3 hours** for orphans and the counter. The “should there be a retention job at all” question is a decision.

27. **`audit_log` is unused.** Table plus RLS, no inserts anywhere under `src`. **3 hours** to write useful events, or about an hour to drop the table. The public pages no longer claim the log exists.

28. **`payer_templates` (“Stickiness Engine”) is unused.** Same shape: schema only. **1 hour** to remove, longer if the feature is actually wanted.

29. **The 835 builder silently balances.** If billed minus paid does not equal the adjustments, it inserts CO-45 or OA-23 (`src/lib/export/x12-generator.ts`). Export then returns 422 only when the validator still fails. The reviewer does not see the invented lines. **3 hours** to show them before download.

30. **CSV dates can shift a day.** `formatDateDentrix` does `new Date("YYYY-MM-DD")`, which is UTC midnight, then uses local `getDate()`. In US timezones that is the previous calendar day. **1 hour.**

31. **Polar webhook bugs.** On `subscription.updated`, if the subscription id is missing and the code finds the practice by email, it writes the id and then `break`s because `practice?.id` is still empty, so the status is not applied. `order.created` sets `pro` from the customer email without checking that the order was paid. **3 hours.** Not changed in this PR.

32. **`PATCH /api/eobs/[id]` writes the JSON body straight through.** RLS keeps the row inside the account. Any column on that row can be set. **2 hours** for an allowlist.

33. **`/api/keep-alive` is public.** If `CRON_SECRET` is unset, the check is skipped and the handler uses the service role when that key exists. Failures return `error.message`. **1 hour** to require the secret and return a generic error.

34. **Feedback `POST` returns the raw Supabase error string.** **0.5 hour.**

35. **No automated tests** for extraction parsing, the first-patient cut, balancing, CSV dates, or the public-route list. **6 hours** for a small set around those.

36. **PMS files are hand-rolled and unverified.** Dentrix, Eaglesoft, and Open Dental CSVs are different column layouts. The 835 generator is large and untested against a real PMS import. **4 hours** to run sample files through one PMS or to label the formats as best-effort in the guide.

Migration 003 tightens storage so a user can only read `{their practice id}/...`. Migration 001 let any signed-in user read every PDF. This audit did not query the live database, so confirm 003 has been applied in the Supabase project. **0.5 hour** to check, included in the keep-alive / security hour above rather than added again.

## Decisions for Adhil

These were left alone on purpose.

- **Billing.** Polar stays at $29/month, with a 14-day trial, 100 PDFs a day during the trial, and 1 PDF a day after it ends. Signup still says “14 days free • 100 PDFs/day • No credit card required.” That matches the code. It is a real checkout on a portfolio project that is about to be emailed to prospects. Turn it off, or keep it and say so in the first email.
- **The Pro bypass.** Item 7. Closing it changes how the daily cap and `subscription_status` are written. Needs a trigger or a service-role update so Settings can still save the practice name.
- **Auth stays as it is.** Email code and Google, two pages, header button that says Google and links to `/signup`. Item 8 (the `next` redirect) is a small fix that does not change the normal sign-in path. Say if you want it in a follow-up.
- **Public demo.** Item 9. Not built here. It is the main reason a stranger cannot tell what the product does.
- **Scans, multi-patient EOBs, audit log, retention.** Items 22, 23, 26, and 27. Either build them or keep the new copy, which already says scans are skipped, nothing is auto-deleted, and there is no audit log.
- **OpenRouter.** Document text leaves the browser for `openai/gpt-4o-mini` with no zero-retention flag. Fine for fictional data. Not fine for real charts. The notice tells people not to upload real charts. A hard block is a product choice.

## Checklist map

Required for this app: public demo entry, honest empty and error states, review before export, phone layout, sign-out confirm, in-app Back, one obvious upload, fictional sample data.

Useful later: keyboard-only focus rings, styled delete confirms, a real side-by-side PDF review, a short test suite.

Skip: team roles, notification center, command palette, dark mode (the `.dark` tokens are a copy of the light theme, and there is no toggle), account deletion UI until the retention decision is made.

Out of scope for a portfolio piece unless Adhil says otherwise: workforce HIPAA training, BAAs, breach-notice process, and any claim that this hosts real patient data.
